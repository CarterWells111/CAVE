# 双人报告分步方案（评审草案）

状态：**已接入后端内测流程，尚未用真实模型试跑或发布**。用户已选择先做分步流程，不测试更强模型。三段标题、图片导出、AI 草稿与手记草稿的展示契约保持 `paired-report-v0.2`；本目录只改变生成前的私有流程。

## 目标与流程

1. **服务端前置检查**：成年人资格、双方本次共享同意、房间快照版本、字段长度和安全风险。出现胁迫、暴力、无视暂停、阻止离开或不能自由拒绝时直接给原有固定 `paused`，不得调用模型或生成共同报告；材料不足则固定 `insufficient`。
2. **第一阶段抽取**：模型按 [事实账本契约](fact-ledger.schema.json) 和 [抽取指令](extract-prompt.md) 提议 A/B 原子事实。每条带回答 ID、原文中连续的精确片段、受控事实代码及适用条件；双方关系分成 `shared`（同一事实）、`compatible`（不同但可相容）、`different`（具体差别），未定事项另列。服务端验证后生成规范化账本与 SHA-256。原始回答沿用现有房间加密存储；中间账本、计划和拒绝原因只在本次内存处理中使用，不进入 API、日志或持久化。
3. **第二阶段编排**：模型只看已验证账本与允许的模板，按 [计划契约](report-plan.schema.json) 和 [编排指令](compose-prompt.md) 选关系 ID、行动和注意点。计划须绑定账本、目录、模板三个内容散列；服务端再次验证引用与模板前提，然后用固定文案渲染恰好三段。模型无权写最终自然语言正文。最终仍由现有加密报告字段存储，API 对外只给三段正文；内部证据 ID 不展示、导出或预填。

`compatible` 必须分人称表达。例如 A 写“是否再谈由我另行提出”，B 写“等对方提出”，账本可记为一对相容事实；正文只能写“A提出，B愿等”，不能写“双方都提出”，也不能把“B是否愿等”放进未定事项。A 自己说停后要独处一小时的条件不能扩成任一方暂停后的通用规则。

内部关系判断和正式报告统一使用 A/B 标识：A 是房间发起人，B 是受邀者。正文中的 `{side}` / `{other}` 由服务端替换为 A/B；App 展示及导出时解释对应关系。

## 由固定模板渲染的三段示例

以下文字由 [暂停情景事实账本](example-pause-ledger.json)、[编排计划](example-pause-plan.json)、[代码目录](fact-catalog.json)与[渲染模板](render-templates.json)经 `python scripts/check_two_stage_report_design.py` 实际组合生成；[完整 JSON](example-pause-report.json)保留内部证据 ID 供校验，页面只显示正文。AI 负责提议事实代码和选择计划，最终文字由服务端模板生成，没有自由扩写步骤。

**共同点与差异**

双方都认为暂停时应停止触碰。A说明由自己另行提出是否再谈，B表示等A提出再谈。差异在于，A担心暂停后还要解释原因，B担心之后不知道是否还能再谈。

**给你们的建议**

可以一起讨论彼此不同的担忧。说出暂停后先停下，不要求当场继续讨论。暂停后不要求对方立刻解释原因。

**接下来的建议**

若双方愿意，听到暂停先停止触碰；之后是否继续，依当时的边界和意愿决定。A说出暂停后，需要一小时独处。如情景变化，再核对彼此边界。

## 可验证的边界

服务端能够机械核对：JSON Schema；每个 `sourceSpan` 必须是相应非空回答里的连续子串，且 `owner` 与 `answerId` 同边；`code`、`scope` 在 [受控目录](fact-catalog.json)内并通过该代码的来源判定规则；ID 唯一且引用存在；`shared` 必须各有一个 A/B 事实、代码一致且条件相同或在经审核的互补条件表内；`compatible` 必须命中目录中的代码对；`different` 必须各有一边、议题相同且两项表态确有区分。`one_sided_proposal` 需要另一方在同一决定上确无相容表态；双方已表明相反选择时用 `unresolved_choice`，不能说某人的立场未知。计划必须绑定账本哈希、满足模板使用条件、三段长度上限和内部证据规则。

**精确片段只证明文字确实来自回答，不能证明事实代码在语义上正确。**服务端已为目录中的代码实现首版中文来源判定，并校验归属、否定、条件与关系；这些规则尚未用真实模型输出校准。自由回答中的转折、代词、隐含压力以及未列入目录的表达，仍可能让第一阶段分类出错。对无法验证的代码和 `other` 停止生成或返回 `insufficient`，不能仅因模型给出 A/B 各一个证据 ID 就承认共识。对安全不确定继续按安全路径暂停。最终自然语言来自受控模板，可阻止第二阶段凭空加“关系疏远”“到家报平安”等新事实；如果目录本身解释错输入，分步流程也不能自动纠正。

## 首版覆盖与时限

目录目前只覆盖三个既定情景中常见说法，主要来自合成样例。真实用户仍可能落入 `other` 或 `insufficient`；这是内测限制。经正反例验证后可纳入同义表达与口语，但不能放宽来源、归属、否定和条件检查。[合成案例](cases.json)除了原有八例，还加入“做顿饭/晚餐一起吃”“六十分钟/等你主动开启话题”两组词面不同但含义相同的改写、明确相反选择，以及完全没有差异的输入。只有共同点、没有可证实差异时，可输出 `ready` 并用固定句如实说明；不制造分歧或未定事项。它们是**预期结果**，不是已经跑过的模型结果；新增表达要通过正例和否定/条件反例才能进入目录来源规则。

现有报告服务总超时为 30 秒、单次模型调用上限约 15 秒。接入两次串行调用时须改成一个共享截止时间，包含前置检查、两次调用、账本校验、渲染和加密；建议先给抽取约 12 秒、编排约 10 秒并留余量，具体值用本地延迟证据定。进入第二阶段前如剩余时间不足，直接返回可重试错误或中性信息不足，不允许延长到两个完整 15 秒或放出未验证报告。计划与账本只在内存里，不改现有房间 API 和加密持久化契约。
