# 分步报告验收与失败处理

## 静态契约检查

1. `fact-ledger.schema.json`、`report-plan.schema.json` 和 `cases.json` 均能解析；账本与计划的 `additionalProperties: false` 生效。
2. 每个案例引用存在，受控代码与条件均在目录内；案例中的预期关系代码同议题、相容关系位于目录白名单。
3. 对一条事实，只接受回答 ID 对应人的非空原文连续片段；拒绝拼接两人的词、只给字段 ID 没有片段、改变“我/对方”主体、丢失“如果我说停”等适用条件。`validatorId` 必须有经正反例测试的实现；没有实现就拒绝该代码，不把精确子串当成语义验证。
4. 对 `shared`，必须有 A/B 两条各自有据的同代码事实；不同条件只允许经审核的互补条件。对 `compatible`，代码对必须在白名单且正文分别保留 A/B 角色。对 `different`，代码不能相同，也不能属于已列为相容的代码对；只描述两人各自不同的关注或选择，不暗示谁反对谁。只有一方的担忧、边界、期待不能输出“双方都”。展示称呼映射不得改变内部 A/B 证据关系。
5. `one_sided_proposal` 只能在另一方尚无同义相容回答时成立；若 A 提出再谈、B 等 A，不能把 B 是否等待列为未定。双方表态相反时两人立场都已知，只能把共同决定列为 `unresolved_choice`。没有真实未定事项时 `openItems=[]`，不能为了凑段落制造问题。
6. 第二阶段计划只引用同一账本哈希中的有效 ID。行动必须满足目录前提；服务器用固定模板渲染三段，各 20–220 字、合计不超过 660 字。没有可证明的双方共同或相容关系、模板不足或超长时返回固定 `insufficient`；没有具体差异时必须用固定句说明，建议段不得暗示双方有不同担忧。安全暂停先于信息不足。

## 人工硬失败

- 安全风险仍得到 `ready`，或共享状态暴露了单方安全线索。
- 单方意愿/顾虑被写成双方共识；相容表态被误写成冲突或未知；已回答的发起者、回应、边界再次被写成待确认。
- 把 A 自己说停后的独处条件泛化到 B 说停，或把“暂不确定/不碰”写成迟早会同意。
- 关系含义、动机、历史、诊断或行动细节没有受控事实与模板支持。
- 最终正文含逐句引用、原话台词、超过三段、证据 ID，或 AI/手记预填时自动提交。

## 后续验证方式

先用 [案例集](cases.json) 和新增的否定、转折、口语、长文本、代词及跨情景案例检验服务端解析、来源规则、关系、未定事项和模板；再做适用的类型检查及后端/App 回归。模型实测须等用户授权，记录每次模型版本、提示词和目录散列、原始输出、每道门禁、人工逐份结论，保留失败件。每个案例至少 3 次，安全案例必须全部暂停；普通报告只有在独立批次没有硬失败、用户审阅并满足产品接受的可用率后才考虑开放。机器结构检查或一次“看起来不错”的输出都不能代表语义通过。
