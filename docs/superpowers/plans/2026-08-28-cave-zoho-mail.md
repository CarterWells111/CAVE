# 内界 CAVE Zoho Mail Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Create a real `support@neijiecave.com` mailbox in Zoho's EU data center and authenticate its mail with MX, SPF, DKIM, and staged DMARC.

**Architecture:** Zoho Mail EU hosts incoming and outgoing support mail. Cloudflare remains the authoritative DNS provider. A single real mailbox handles support; `dmarc@neijiecave.com` is a management alias that files aggregate reports into a dedicated folder.

**Tech Stack:** Zoho Mail EU, Cloudflare DNS, SMTP email standards (MX, SPF, DKIM, DMARC)

---

### Task 1: Create the EU organization safely

- [ ] Open `https://accounts.zoho.eu/` directly and create the administrator with a long-term personal email.
- [ ] Verify the account inside Zoho; do not send the password, verification code, recovery information, or session link into chat.
- [ ] After login, confirm the browser address uses `.zoho.eu`. Stop if it uses `.com`, `.in`, `.com.au`, or another data center.
- [ ] Select the free custom-domain plan if the EU data center offers it. If not, stop at the price screen and obtain user approval before choosing Mail Lite.
- [ ] Create the organization under the public operator name `ZHIQI LIANG`, using `内界 CAVE` only as the brand/display name.

Expected: one EU Zoho organization exists with a verified personal recovery/admin account and no unapproved payment.

### Task 2: Verify domain ownership

- [ ] In Zoho Mail Admin Console, open Domains > Add and enter `neijiecave.com`.
- [ ] Choose manual TXT verification rather than granting broad Domain Connect access.
- [ ] Copy the exact TXT host and value generated by Zoho.
- [ ] In Cloudflare DNS, create that TXT record with TTL Auto. TXT records are DNS-only by definition.
- [ ] Return to Zoho and select Verify. If it does not verify, wait for propagation and inspect the exact host/value; do not create duplicate verification records.
- [ ] After success, record only the public DNS host/type and Zoho verification status, not the administrator credentials.

Expected: Zoho reports domain ownership Verified.

### Task 3: Create the support mailbox and DMARC alias

- [ ] Create the only real domain user as `support@neijiecave.com` with display name `内界 CAVE 支持`.
- [ ] Set locale to Simplified Chinese and timezone to Europe/London.
- [ ] Create `dmarc@neijiecave.com` as an alias that delivers to the support mailbox; do not consume a separate licensed user.
- [ ] Create a mailbox folder named `DMARC 报告` and a rule that moves messages addressed to the DMARC alias into it.
- [ ] Add a concise signature containing `内界 CAVE`, `support@neijiecave.com`, and `https://neijiecave.com`; do not include medical or emergency-service claims.

Expected: both addresses receive into the support mailbox, with DMARC reports separated from support requests.

### Task 4: Configure incoming mail with Zoho EU MX

- [ ] In Zoho Admin Console, open the domain's Email Configuration > MX and copy the exact EU hostnames and priorities shown there.
- [ ] In Cloudflare DNS, inspect existing MX records for the apex. Stop before deleting any record whose owner or purpose is unknown.
- [ ] Because this is a newly purchased domain with no prior mail service, remove only confirmed parking/default MX records, then add the Zoho-provided MX records with their exact priorities and TTL Auto.
- [ ] Ensure every MX target is entered as DNS-only and no A/AAAA/CNAME record pointing to an MX target is proxied.
- [ ] Return to Zoho and wait for MX Verified.
- [ ] Send a message from a personal external mailbox to `support@neijiecave.com` and confirm receipt.

Expected: Zoho MX status Verified and inbound external mail arrives.

### Task 5: Configure SPF and DKIM

- [ ] Search Cloudflare DNS for all apex TXT records beginning `v=spf1`.
- [ ] If none exists, add the exact SPF value shown by Zoho EU. If one exists, merge Zoho into that one record; never publish two SPF records.
- [ ] Return to Zoho and wait for SPF Verified.
- [ ] In Zoho DKIM settings, create selector `zmail` and copy the generated public key record.
- [ ] In Cloudflare, create the exact TXT host Zoho displays (normally `zmail._domainkey`) with the complete public value and TTL Auto.
- [ ] Return to Zoho, select Verify, then explicitly Enable the verified selector for signing.
- [ ] Send one message to a personal Gmail address and inspect Show original. Require SPF `PASS` and DKIM `PASS` with alignment to `neijiecave.com`.

Expected: Zoho shows SPF and DKIM Verified/Enabled; an external message passes both.

### Task 6: Publish monitoring-mode DMARC

- [ ] Confirm `dmarc@neijiecave.com` receives mail before publishing the policy.
- [ ] Confirm no existing `_dmarc.neijiecave.com` TXT record exists. Stop and inspect if one is present.
- [ ] Add `_dmarc` TXT with exact value:

```text
v=DMARC1; p=none; rua=mailto:dmarc@neijiecave.com; adkim=s; aspf=s; pct=100
```

- [ ] Wait for Zoho or an independent DNS lookup to show the single DMARC record.
- [ ] Send a new external test and require DMARC `PASS` in the recipient's original headers.
- [ ] Keep `p=none` for at least 14 days. Do not tighten the policy merely because one test message passed.

Expected: one DMARC record exists, aligned Zoho messages pass, and aggregate reports reach the alias.

### Task 7: Cross-provider acceptance test

- [ ] From support, send distinct plain-text messages to Gmail, Outlook, and iCloud test recipients.
- [ ] Reply from each provider and confirm all three replies arrive at support.
- [ ] Inspect each received outbound message for SPF, DKIM, and DMARC `PASS`.
- [ ] Send to a random nonexistent address at `neijiecave.com` and confirm it bounces rather than landing in support; keep catch-all disabled.
- [ ] Open `https://neijiecave.com/support`, activate its mail link, and complete one real support round trip.
- [ ] Record public DNS records, Zoho verification statuses, test providers, and dates. Do not store full message bodies, personal recipient addresses, raw headers containing identifiers, or credentials in the repository.
- [ ] Send the final support address and successful authentication status to the main App task for App Store Support URL and privacy-policy review.

Expected: support mail works bidirectionally across all three providers with authenticated delivery.

### Task 8: Stage stronger DMARC after observation

- [ ] After at least 14 full days, review aggregate reports in `DMARC 报告` and list every legitimate source.
- [ ] If Zoho is the only source and all legitimate mail aligns, change only `p=none` to `p=quarantine; pct=25` while preserving `rua`, `adkim`, and `aspf`.
- [ ] Observe at least 7 additional days. If there are no legitimate failures, raise `pct` to 100.
- [ ] Observe another 7 days, then evaluate `p=reject`; stop if any legitimate source fails alignment.
- [ ] Before adding Resend in a future account-enabled release, return DMARC to a non-destructive observation state if necessary, verify the `auth` subdomain independently, and never add a second root SPF record.

Expected: policy strength increases only from evidence and never disrupts legitimate support mail.
